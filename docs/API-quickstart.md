# 管理 API 快速上手 / Admin API quickstart

用 curl 从零走完「新建项目 → 上传 → 抽取 → 核对并修改事实 → 确认 → 生成 → 发布」。下面的命令按顺序复制执行即可串起来；每一步都写明了请求体和关键响应字段。路由总表见 [CONTRACT.md 第 6 节](CONTRACT.md#6-api-路由)。

Walk through "create project → upload → extract → review and edit facts → confirm → generate → publish" with curl. Copy the commands below in order; each step lists the request body and the response fields used next. The full route table is in [CONTRACT.md section 6](CONTRACT.md#6-api-路由).

## 准备 / Before you start

- 服务已启动（`pnpm demo` 或 `pnpm dev`，或 Docker 的 `docker compose up`），监听 `http://localhost:6688`。命令在仓库根目录执行，示例使用 `eval/samples/bakery-dessert-menu` 的两张图片和原始文字。
- 需要 `curl` 和 `jq`（用来从响应里取 id）。没有 jq 时，可以去掉 `| jq ...`，从响应里手动复制对应的值赋给变量。
- 除公开页外，下面所有请求都要带管理口令：请求头 `Authorization: Bearer $ADMIN_TOKEN`。

- The server is running on `http://localhost:6688` (`pnpm demo`, `pnpm dev`, or `docker compose up`). Run the commands from the repository root; the example uses the two images and the raw text of `eval/samples/bakery-dessert-menu`.
- You need `curl` and `jq` (to pick ids out of responses). Without jq, drop the `| jq ...` part and copy the values from the responses by hand.
- Every request below except the public page needs the admin token in the header `Authorization: Bearer $ADMIN_TOKEN`.

```bash
BASE=http://localhost:6688
# 本地运行：口令在 pnpm bootstrap 生成的 .env 里 / local run: the token is in the .env written by pnpm bootstrap
export ADMIN_TOKEN="$(sed -n 's/^ADMIN_TOKEN=//p' .env)"
# Docker 自动生成的口令改用 / for a token generated by Docker, use instead:
# export ADMIN_TOKEN="$(cat data/admin-token)"
AUTH="Authorization: Bearer $ADMIN_TOKEN"
```

如果你在 `.env.local` 或命令行环境变量里另设了 `ADMIN_TOKEN`，服务以那个值为准，请改用它。

If you set `ADMIN_TOKEN` in `.env.local` or the shell environment, the server uses that value instead; use it here too.

## 1. 新建项目 / Create a project

`type` 为 `single`（单品）或 `menu`（菜单），`title` 为 1–30 个字符。返回 201 `{ id, slug }`。

`type` is `single` or `menu`; `title` is 1–30 characters. Returns 201 `{ id, slug }`.

```bash
curl -sS -X POST "$BASE/api/projects" -H "$AUTH" \
  -H 'Content-Type: application/json' \
  -d '{"type":"menu","title":"甜心烘焙坊"}' | tee /tmp/shizhao-project.json
PROJECT_ID=$(jq -r .id /tmp/shizhao-project.json)
SLUG=$(jq -r .slug /tmp/shizhao-project.json)
```

## 2. 上传图片和文字 / Upload images and text

`multipart/form-data`：每张图片一个 `images` 字段（可重复），商家文字放在 `text` 字段（可选）。`text=<文件路径` 是 curl 的写法，表示把文件内容作为字段值发送。返回 201 `{ assets }`。

`multipart/form-data`: one `images` field per image (repeatable) and the merchant's text in the optional `text` field. `text=<path` is curl syntax for sending the file's content as the field value. Returns 201 `{ assets }`.

```bash
curl -sS -X POST "$BASE/api/projects/$PROJECT_ID/assets" -H "$AUTH" \
  -F images=@eval/samples/bakery-dessert-menu/images/egg-tart.png \
  -F images=@eval/samples/bakery-dessert-menu/images/menu.png \
  -F 'text=<eval/samples/bakery-dessert-menu/input.txt'
```

同一次请求上传的多张图片创建时间相同，之后按素材 id 排列，不保证保持上传顺序。Mock 按素材顺序把图片配给商品，所以上面的写法下，商品配图可能对调（事实表的文字和价格不受影响）。需要固定顺序时，改为每张图片单独上传一次，最后单独上传文字（`pnpm demo` 就是这样做的），用它代替上面的命令：

Images uploaded in one request share a creation time and are then listed by asset id, so their upload order is not guaranteed. The mock assigns images to products in asset order, so with the command above two product photos may swap (fact text and prices are unaffected). If order matters, upload one image per request and the text last (as `pnpm demo` does), instead of the command above:

```bash
# 替代写法 / alternative
for img in egg-tart menu; do
  curl -sS -X POST "$BASE/api/projects/$PROJECT_ID/assets" -H "$AUTH" \
    -F "images=@eval/samples/bakery-dessert-menu/images/$img.png"
done
curl -sS -X POST "$BASE/api/projects/$PROJECT_ID/assets" -H "$AUTH" \
  -F 'text=<eval/samples/bakery-dessert-menu/input.txt'
```

## 3. 抽取事实 / Extract facts

没有请求体。返回 201 `{ factSheet, conflicts, lowConfidenceFields }`，`factSheet` 是新 revision（第一次为 1）的**未确认**事实表。

No request body. Returns 201 `{ factSheet, conflicts, lowConfidenceFields }`; `factSheet` is a new, **unconfirmed** revision (1 the first time).

```bash
curl -sS -X POST "$BASE/api/projects/$PROJECT_ID/extract" -H "$AUTH" | tee /tmp/shizhao-extract.json
jq '.factSheet | {revision, shop, items: [.items[] | {name, price, spec}]}' /tmp/shizhao-extract.json
```

**逐项核对。** Mock 模型返回固定的模型草稿，仍会经过事实抽取与校验，可能漏掉字段；`conflicts` 和 `lowConfidenceFields` 为空也不代表没有遗漏。这组样本里，原文「巴斯克芝士蛋糕 6 寸 128 元」的价格目前会漏抽（已知问题，见 README「已知限制」），下一步要补上。

**Check every field.** The mock model returns a fixed model draft that still goes through extraction and validation, so fields can be missing, even when `conflicts` and `lowConfidenceFields` are empty. In this sample the price in "巴斯克芝士蛋糕 6 寸 128 元" is currently missed (a known issue, see "Known limitations" in the README); the next step adds it.

## 4. 修改事实表 / Edit the fact sheet

`PUT /api/projects/:id/facts` 的请求体是一份**完整**事实表：去掉服务器字段 `projectId`、`revision`、`confirmedAt`，加上 `baseRevision`（你核对的那个 revision）。如果期间有人保存了更新的 revision，返回 409，需要重新读取再改。成功返回 `{ factSheet }`，其中是新 revision（这里为 2，未确认）。

The body of `PUT /api/projects/:id/facts` is a **complete** fact sheet without the server fields `projectId`, `revision` and `confirmedAt`, plus `baseRevision` (the revision you reviewed). If a newer revision was saved meanwhile you get 409; reload and edit again. Success returns `{ factSheet }` with the new, unconfirmed revision (2 here).

下面用 jq 从抽取结果生成请求体，只补上漏掉的价格。原文没写单位，所以不加 `unit`。

The jq below builds the body from the extraction result and only adds the missing price. The source text gives no unit, so no `unit` is added.

```bash
jq '.factSheet
    | .baseRevision = .revision
    | del(.projectId, .revision, .confirmedAt)
    | (.items[] | select(.name == "巴斯克芝士蛋糕")).price = {"amount":128,"currency":"CNY"}' \
  /tmp/shizhao-extract.json > /tmp/shizhao-facts-edit.json

curl -sS -X PUT "$BASE/api/projects/$PROJECT_ID/facts" -H "$AUTH" \
  -H 'Content-Type: application/json' \
  --data-binary @/tmp/shizhao-facts-edit.json | jq '.factSheet | {revision, confirmedAt}'
```

请求体的结构如下（商品 `id` 用抽取结果里的值，不要自己编）：

The body looks like this (keep the item `id`s from the extraction result; do not invent them):

```json
{
  "shop": { "name": "甜心烘焙坊", "phone": "139 0000 0000", "wechat": "tianxin_bake" },
  "items": [
    { "id": "<抽取返回的商品 id>", "name": "葡式蛋挞", "price": { "amount": 8, "currency": "CNY", "unit": "个" },
      "tags": [], "imageAssetIds": ["<图片素材 id>"], "sources": { "name": "merchant_text", "price": "merchant_text" } },
    { "id": "<抽取返回的商品 id>", "name": "巴斯克芝士蛋糕", "spec": "6 寸", "price": { "amount": 128, "currency": "CNY" },
      "tags": [], "imageAssetIds": [], "sources": { "name": "merchant_text", "spec": "merchant_text" } }
  ],
  "extraClaims": ["可预订"],
  "baseRevision": 1
}
```

## 5. 确认事实表 / Confirm the facts

请求体 `{ "revision": <你核对过的 revision> }`，它必须仍是最新 revision，否则返回 409 `facts_changed`。生成只使用已确认的事实表。上一步保存了 revision 2，所以这里确认 2；如果抽取结果无需修改、跳过了第 4 步，就确认 `{"revision":1}`。

Body `{ "revision": <the revision you reviewed> }`; it must still be the latest, otherwise 409 `facts_changed`. Generation only uses confirmed facts. Step 4 saved revision 2, so confirm 2; if nothing needed editing and you skipped step 4, confirm `{"revision":1}`.

```bash
curl -sS -X POST "$BASE/api/projects/$PROJECT_ID/facts/confirm" -H "$AUTH" \
  -H 'Content-Type: application/json' \
  -d '{"revision":2}' | jq '.factSheet | {revision, confirmedAt}'
```

## 6. 生成 / Generate

没有请求体。返回 202 `{ jobId }`，任务在后台运行。没有已确认的事实表时返回 409 `facts_not_confirmed`，已有任务在运行时返回 409 `job_running`。

No request body. Returns 202 `{ jobId }`; the job runs in the background. 409 `facts_not_confirmed` without confirmed facts, 409 `job_running` while another job runs.

```bash
JOB_ID=$(curl -sS -X POST "$BASE/api/projects/$PROJECT_ID/jobs" -H "$AUTH" | jq -r .jobId)
echo "$JOB_ID"
```

## 7. 轮询任务 / Poll the job

`GET /api/jobs/:id` 返回 `{ status, stage, stageLabel, etaSeconds, startedAt, error? }`。`status` 依次经过 `queued`、`designing`、`writing`、`guarding`、`rendering`、`checking`，终态为 `succeeded`、`failed` 或 `timed_out`。

`GET /api/jobs/:id` returns `{ status, stage, stageLabel, etaSeconds, startedAt, error? }`. `status` moves through `queued`, `designing`, `writing`, `guarding`, `rendering`, `checking` and ends in `succeeded`, `failed` or `timed_out`.

```bash
while :; do
  STATUS=$(curl -sS "$BASE/api/jobs/$JOB_ID" -H "$AUTH" | jq -r .status)
  echo "$STATUS"
  case "$STATUS" in succeeded|failed|timed_out) break ;; esac
  sleep 1
done
```

## 8. 列出版本 / List versions

返回 `{ versions }`，最新的在前；每个版本带 `factRevision`，表示它基于哪个 revision 生成。

Returns `{ versions }`, newest first; each version carries `factRevision`, the fact revision it was built from.

```bash
curl -sS "$BASE/api/projects/$PROJECT_ID/versions" -H "$AUTH" | tee /tmp/shizhao-versions.json \
  | jq '.versions[] | {id, factRevision, templateId}'
VERSION_ID=$(jq -r '.versions[0].id' /tmp/shizhao-versions.json)
```

## 9. 发布 / Publish

请求体 `{"versionId":"<版本ID>","factsConfirmed":true}`。`factsConfirmed` 必须是 `true`，表示商家已经核对过这个版本页面上的事实；只有在核对后才能设为 `true`，缺少或为 `false` 时返回 400 `invalid_input`。返回 `{ url, qrPngUrl, qrSvgUrl }`。

Body `{"versionId":"<version id>","factsConfirmed":true}`. `factsConfirmed` must be `true`, meaning the merchant has checked the facts on this version's page; set it only after that check. Missing or `false` returns 400 `invalid_input`. Returns `{ url, qrPngUrl, qrSvgUrl }`.

```bash
curl -sS -X POST "$BASE/api/projects/$PROJECT_ID/publish" -H "$AUTH" \
  -H 'Content-Type: application/json' \
  -d "{\"versionId\":\"$VERSION_ID\",\"factsConfirmed\":true}"
```

## 10. 打开公开页 / Open the public page

公开页不需要口令，地址带结尾斜杠。应返回 `200`。

The public page needs no token; the URL ends with a slash. Expect `200`.

```bash
curl -sS -o /tmp/shizhao-page.html -w '%{http_code}\n' "$BASE/p/$SLUG/"
```

浏览器打开 `http://localhost:6688/p/<slug>/` 即可看到页面。之后改了事实表，重复第 4–9 步：重新确认、生成、发布，短链接和二维码保持不变。

Open `http://localhost:6688/p/<slug>/` in a browser to see the page. After further fact edits, repeat steps 4–9 (confirm, generate, publish again); the short link and QR code stay the same.
